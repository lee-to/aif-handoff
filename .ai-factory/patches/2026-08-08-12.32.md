# GitHub issue-to-PR rollout and Actions check status fixes

**Date:** 2026-08-08 12:32 MSK
**Files:** packages/shared/src/env.ts, packages/api/src/routes/github.ts, packages/api/src/services/github.ts, packages/api/src/routes/settings.ts, packages/agent/src/githubWorkflow.ts, packages/agent/src/subagents/planner.ts, packages/web/src/components/project/ProjectSelector.tsx, related tests and documentation
**Severity:** high

## Problem

GitHub issue synchronization, task worktree provisioning, branch pushes, pull-request publication, and task-state updates became active as soon as a project connection existed. Pull-request CI state also read only legacy commit statuses, so repositories using GitHub Actions check runs could report pending or miss failures.

## Root Cause

The new external automation path shipped without an environment-controlled compatibility boundary. Its CI aggregation also assumed that every provider reports through the legacy commit-status endpoint, although GitHub Actions uses the checks API.

## Solution

- Added `AIF_GITHUB_ISSUE_PR_ENABLED`, defaulting to `false`, and gated API routes, UI controls, agent polling/publication, and planner issue-specific worktrees.
- Kept saved linkage intact while disabled so rollout is reversible without data loss.
- Combined paginated GitHub check runs with legacy commit statuses using failure-before-pending-before-success precedence.
- Added structured `[FIX:154]` debug logs and regression coverage for disabled behavior plus Actions-only success and failure results.

## Prevention

- Put new external calls, Git mutations, and coordinator state-machine behavior behind an off-by-default rollout flag.
- Treat GitHub commit statuses and check runs as separate signal sources and aggregate both.
- Cover the flag-off compatibility path and provider-specific CI reporting before enabling automation.
