# PR 169 follow-up review fixes

**Date:** 2026-08-03 16:35 MSK
**Files:** participant authentication, WebSocket integration tests, runtime logs, state-machine guidance, and security/API documentation
**Severity:** medium

## Problem

The follow-up review requested stricter session cookies, removal of temporary fix tags from production logs, and clarification of workspace-wide comments, WebSocket delivery, and the `improve` stage.

## Root Cause

The cookie retained the original `SameSite=Lax` setting, review-specific prefixes remained after the first fix, and intentional shared-workspace behavior was not explicit in tests or documentation.

## Solution

- Changed participant session cookies to `SameSite=Strict`; existing production and HTTPS detection continues to set `Secure`.
- Removed temporary `[FIX:*]` prefixes while preserving structured operational logs.
- Documented workspace-wide task/project events and comment access.
- Clarified that status-only human actions are legacy metadata; owner-aware permissions come from `resolveTaskPermissions()`.
- Kept the existing targeted session-revocation implementation and added a two-participant regression proving it does not leak to other sockets.

## Verification

- Cookie regression passes with `SameSite=Strict`.
- Both WebSocket transports pass the two-participant targeted-revocation regression.
- No temporary `[FIX:*]` production log tags remain.
- `npm run ai:validate` passes.

## Prevention

- Encode security cookie attributes in tests.
- Test participant-targeted events with an authenticated observer connection.
- Keep intentional shared-workspace authorization boundaries explicit in API and security documentation.
