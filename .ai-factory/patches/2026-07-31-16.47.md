# Participant bootstrap and ownership UI follow-up

**Date:** 2026-07-31 16:47 MSK
**Files:** `packages/api/src/scripts/bootstrapParticipantAdmin.ts`, `packages/web/src/components/ui/dropdown-menu.tsx`, `packages/web/src/components/kanban/Board.tsx`, `packages/web/src/components/kanban/FilterBar.tsx`
**Severity:** medium

## Problem

The first-admin command required several flags and `--password-stdin` waited for EOF when used from a terminal. The participant menu appeared not to open, and the Human-owned task filter could not narrow tasks by assignee.

## Root Cause

- Bootstrap supported automation inputs only; it had no terminal prompt path.
- The dropdown `asChild` trigger measured a `display: contents` wrapper. Chromium reports a zero-sized rectangle for that wrapper, so the end-aligned menu was positioned outside the viewport.
- Board filtering tracked ownership but not selected assignee identities.

## Solution

- No-argument bootstrap now prompts for identity and reads a hidden password twice, while existing protected-file/stdin flags remain unchanged for automation. Non-TTY no-argument calls fail immediately with actionable guidance.
- The shared dropdown trigger now uses a measurable inline-flex wrapper.
- Human-owned filtering now exposes assignee chips derived from visible task ownership data and applies OR matching across selected assignees.
- Regression tests cover interactive validation, measurable dropdown triggers, and assignee filtering.

## Prevention

- Separate interactive CLI defaults from explicit automation flags, and never read terminal secrets by waiting for EOF.
- Position overlays from elements that generate a layout box; DOM-presence tests alone do not validate geometry.
- When a broad ownership filter groups multiple people, provide identity-level narrowing from the same task data used by the filter.
