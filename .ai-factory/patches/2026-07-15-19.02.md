# Coordinator permit wait could run stale tasks and leak capacity

**Date:** 2026-07-15 19:02
**Files:** packages/agent/src/coordinator.ts, packages/agent/src/__tests__/coordinator.test.ts, packages/agent/CHECKLIST.md, packages/data/src/index.ts, packages/data/src/__tests__/index.test.ts
**Severity:** high

## Problem

Project lanes selected task candidates before waiting for a global semaphore permit. A task could
be paused or moved to another status during a long wait, yet the coordinator would still claim and
run the old snapshot. A synchronous database exception after permit acquisition could also leak the
permit and permanently block queued lanes and future poll cycles.

## Root Cause

The scheduler treated the pre-wait candidate query as authoritative even though semaphore waiting
introduced an unbounded concurrency window. The task claim checked only task ID and lock availability,
and cleanup ownership was split between manual branches and the task promise without a `try/finally`
covering the transfer boundary.

## Solution

Added a coordinator-specific atomic CAS claim that validates project, status, paused state, conditional
`autoMode`, and lock availability, then returns the fresh claimed row through SQLite `RETURNING`.
After every permit wait the coordinator repeats the non-parallel guard and runtime-limit gate, then
uses the fresh row for execution. Permit and owner-scoped claim cleanup now remain under one
exception-safe ownership scope until cleanup is transferred to the task promise. Rejected project
lanes are logged instead of being silently discarded.

Regression tests cover stale paused candidates, runtime-gate changes during permit waits, claim
exceptions with queued lanes, semaphore reuse on a later poll, CAS conflicts, fresh-row returns,
owner-scoped release, and execution of a coalesced follow-up cycle.

## Prevention

- Treat any snapshot read before an async capacity wait as stale until atomically revalidated.
- Return the row produced by a successful CAS when downstream behavior depends on mutable fields.
- Keep permit and lock cleanup in a single `try/finally` until ownership is explicitly transferred.
- Test both cleanup counters and forward progress of queued and subsequent scheduler work.
