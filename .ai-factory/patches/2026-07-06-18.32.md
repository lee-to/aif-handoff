## Problem

The coordinator used a global stage loop and global `StageSemaphore` keys. This let an active task in one project consume the same scheduler lane as unrelated work in another project. A slow early stage could therefore delay a later-stage task in a different project, and the default `COORDINATOR_MAX_CONCURRENT_TASKS=3` acted as a global task cap instead of a per-project cap.

## Root Cause

Candidate selection was global and stage-first. Project concurrency lowered the allowed task count for a single project, but the scheduler never partitioned actionable work into independent project lanes. The semaphore key was also just the stage label, so active counts were shared across all projects for the same workflow stage.

## Solution

The coordinator now selects actionable project lanes with `listCoordinatorActionableProjectIds`, caps them with `COORDINATOR_MAX_CONCURRENT_PROJECTS`, and processes those lanes concurrently. Inside each project lane, stages still run in order, and task limits remain scoped to that project. Candidate queries can now fetch tasks for a specific project and stage, and semaphore keys include both project and stage. A separate global `COORDINATOR_MAX_CONCURRENT_TASKS` safety ceiling bounds aggregate work across all lanes, while `COORDINATOR_MAX_CONCURRENT_TASKS_PER_PROJECT` controls parallel work inside one project. Docs and environment defaults were updated to describe all three limits.

Regression tests cover both observed failure modes:

- A slow planning task in one project must not block a review task in another project.
- Four independent non-parallel projects must all start work when the project lane cap is four, even though the per-project task cap remains three.

## Prevention

Coordinator scheduler changes need cross-project and cross-stage regression coverage, not only single-project task-count assertions. Data-access candidate queries should preserve fairness by project and must be tested with crowded projects plus locked tasks. Documentation and env tests should be updated whenever concurrency semantics change.
