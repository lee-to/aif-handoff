# Project lane exited before draining started tasks

**Date:** 2026-07-16 11:14
**Files:** packages/agent/src/coordinator.ts, packages/agent/src/__tests__/coordinator.test.ts, packages/agent/CHECKLIST.md
**Severity:** high

## Problem

When setup for a later task candidate threw, the project lane rejected before awaiting task promises
that it had already started. The poll could therefore complete and admit a follow-up cycle while an
earlier stage from the same parallel project was still running. A claim exception after the database
write could also leave the coordinator-owned task lock behind.

## Root Cause

The stage-level `Promise.allSettled(spawned)` drain was placed after the candidate loop, so any setup
exception bypassed it. Cleanup also depended only on the assigned `claimedTask`; an exception after an
ambiguous claim write but before assignment left no task ID for the cleanup closure.

## Solution

Moved the stage drain into a `finally` block around the entire candidate loop. This preserves the
original setup exception while waiting for every already-started task and its permit/claim cleanup.
Added a narrow `claimOutcomeUncertain` ownership flag so an exceptional claim path defensively releases
only a lock owned by the current coordinator, while a normal CAS miss cannot clear another active claim.

Regression tests now hold the first planner while the second candidate claim fails, verify the poll
remains single-flight until the planner finishes, and confirm later work can proceed. A second test
performs the real claim write before throwing and verifies that both lock fields are cleared.

## Prevention

- Put async drains in `finally` whenever loop setup can fail after work has already been launched.
- Test scheduler failures after at least one task has started, not only failures on the first candidate.
- Model ambiguous resource-acquisition outcomes explicitly and use owner-scoped idempotent cleanup.
- Verify both promise settlement timing and persisted lock state in concurrency regression tests.
