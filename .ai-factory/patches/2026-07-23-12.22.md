# Auto-queue completion commit gate

**Date:** 2026-07-23 12:22
**Files:** packages/agent/src/autoQueueCommit.ts, packages/agent/src/coordinator.ts, packages/agent/src/subagentQuery.ts, packages/data/src/index.ts, packages/shared/src/commitWorkflow.ts, packages/shared/src/db.ts, packages/shared/src/schema.ts, packages/shared/src/types.ts
**Severity:** high

## Problem

Auto-queue could move a completed task to a terminal status and immediately start the next task while the previous task's changes were still uncommitted. Consecutive tasks then shared an ambiguous Git diff, making task-level rollback, review, and commit attribution unreliable.

## Root Cause

The existing commit workflow was only triggered by an optional API checkbox. The coordinator did not own an awaited completion barrier, did not persist a baseline or resulting commit SHA, and treated terminal task status as sufficient evidence that the Git worktree was ready for the next task.

## Solution

- Record the Git baseline atomically when auto-queue claims a backlog task.
- Await the existing runtime-backed commit workflow before every auto-queue terminal transition.
- Verify that the workflow leaves a clean worktree and creates exactly one commit, then persist its SHA.
- Reconcile an already-created clean commit after coordinator restart without creating a duplicate commit.
- Move commit failures to a manual external block and prevent the next queued task from starting.
- Force serial execution when auto-queue tasks share one Git working tree; isolated task worktrees may still run in parallel.

## Prevention

- Treat external side effects needed by the next queued item as awaited state-machine barriers.
- Persist both the pre-operation baseline and the verified result so restart recovery is idempotent.
- Test the full ordering invariant: task A commits and becomes terminal before task B can be claimed.
- Never use terminal database status alone as proof that a shared mutable resource is clean.
